Como o sistema funciona por dentro

Este documento é para quem vai mexer no RitmoPatrimar Embalagem — não para quem só usa. Ele explica os arquivos, o banco de dados, quem pode o quê, e como fazer uma alteração sem derrubar a TV da fábrica. Tudo com exemplos do sistema de verdade, não de manual.

1. As peças

São três coisas, e só três. Se você entender a divisão entre elas, o resto é detalhe.

PeçaO que éOnde vive
As telas Arquivos HTML soltos. Cada tela é um arquivo único, com o HTML, o CSS e o JavaScript dentro dele. Não há framework, não há build, não há npm install. GitHub → Vercel
O banco Supabase (que é um PostgreSQL com uma API REST na frente). Guarda os vídeos, o que está na TV, os tablets autorizados e as pessoas. projeto crono-analise
As imagens Os desenhos de cada camada, como arquivos JPEG. Ficam no Storage do Supabase, no balde embalagem, não dentro do banco. Supabase Storage
A ideia central: as telas não têm servidor próprio. Elas são arquivos estáticos que rodam no navegador e falam direto com o Supabase. Não existe "back-end" nosso no meio — o que protege os dados são as regras dentro do banco, não um programa nosso.

Isso explica uma coisa que costuma assustar: a chave do Supabase está escrita no supabase-config.js, em texto puro, visível para qualquer um que abrir o site. E está certo. Ela é a chave publicável: sozinha, só permite o que as regras do banco liberam para visitante — no nosso caso, ler os vídeos. Publicar, excluir ou trocar a TV exige estar logado. A chave que pode tudo (service_role) nunca sai do painel do Supabase e nunca entra em arquivo nenhum do site.

2. Os arquivos

ArquivoO que faz
inicio.htmlMenu com os atalhos e as instruções de uso.
gerador.htmlLê o PDF de embalagem, corta as camadas, monta a lista de componentes e publica o vídeo. É o arquivo mais complexo do projeto.
biblioteca.htmlLista os vídeos publicados. Coloca na TV, pausa, ajusta tempo e modo, busca.
configuracoes.htmlAutoriza e revoga os tablets.
nova-senha.htmlRedefinição de senha, aberta pelo link do e-mail.
tv/index.htmlO player da TV. Arquivo fixo: não muda quando você troca de vídeo. Ele é que pergunta ao banco o que exibir.
supabase-config.jsEndereço e chave do Supabase, e as funções de leitura. As quatro telas e a TV carregam este arquivo — é o único compartilhado por todos.
publicar.jsTudo que escreve no banco: login, publicar, trocar a TV, pausar, autorizar tablet. A TV nunca carrega este arquivo, porque a TV nunca escreve.

vercel.jsonDiz que /biblioteca serve o biblioteca.html, e que a raiz do site é a TV.

Por que HTML solto, sem framework?

Porque o player roda no navegador embutido de uma Smart TV, que é um Chromium de 2019. Framework moderno não abre lá. E porque um arquivo único é legível daqui a dois anos por quem não acompanhou a construção — inclusive por você.

3. O banco de dados

O projeto Supabase é o mesmo da cronoanálise (RitmoProd). As tabelas da embalagem têm prefixo embalagem_ e não se misturam com as de lá. A única compartilhada é a de pessoas.

TabelaO que guarda
embalagem_paineisUm vídeo por linha. Colunas: slug (o apelido na URL), produto, tempo (segundos por camada), camadas, fotos, opcoes, atualizado_em.
embalagem_configUma linha só, de id 1. É o "controle remoto" da TV: painel_ativo (o que está no ar), tv_pausa, tv_recarregar.
embalagem_dispositivosOs tablets autorizados: nome, token_hash, ativo, ultimo_acesso_em.
embalagem_pareamentosOs códigos de autorização em aberto. A linha some quando o código é usado.
usuariosCompartilhada com o RitmoProd. Quem é admin, analista, coletor.

Três colunas jsonb, e por quê

camadas, fotos e opcoes guardam JSON — uma estrutura inteira dentro de uma célula. Um vídeo com 8 camadas guarda as 8 numa coluna só, em vez de uma tabela embalagem_camadas com 8 linhas.

Isso é uma escolha, com vantagem e preço. A vantagem: o vídeo é lido e gravado de uma vez, e a estrutura acompanha o que o gerador produz sem migração a cada ajuste. O preço: você não consegue perguntar ao banco "quais vídeos usam a peça LATERAL Nº 03" sem escrever SQL de JSON. Como ninguém nunca precisou dessa pergunta, o JSON ganhou.

-- uma camada, por dentro:
{ "op": "CAMADA 02",
  "obs": "FURACOES PARA CIMA",
  "img": "embalagem-nicho/cam02.jpg",
  "componentes": [ { "qtd": 2, "nome": "PORTA Nº 05" } ] }

RLS: a parte que protege tudo

Row Level Security é a regra que o Postgres aplica em toda consulta, venha de onde vier. Como as telas falam direto com o banco, é aqui — e só aqui — que a segurança mora.

-- ler os vídeos: qualquer um, até sem login
create policy embalagem_paineis_leitura on embalagem_paineis
  for select to anon, authenticated using (true);

-- escrever: só quem passa nesta função
create policy embalagem_paineis_escrita on embalagem_paineis
  for all to authenticated
  using (embalagem_pode_publicar());
A consequência prática: não adianta esconder um botão na tela para "proteger" algo. Quem souber usar o navegador chama a API direto. Esconder o botão é gentileza com o usuário — quem protege é a policy.

As funções

FunçãoPara quê
papel_atual()Devolve o papel de quem está logado, lendo a tabela usuarios. Vem do RitmoProd.
embalagem_pode_publicar()admin ou analista. Governa criar, substituir e excluir vídeo.
embalagem_pode_operar()Mesmo grupo, para as ações de TV feitas por pessoas logadas.
embalagem_parear(codigo)Troca o código pelo token do tablet. É a única função aberta a visitante — o tablet ainda não tem nada quando digita o código.
embalagem_op_ativar, _pausa, _recarregar, _tempo, _exibicao As ações do tablet. Cada uma recebe o token, confere se o aparelho está ativo e faz uma coisa.

Repare no desenho: o tablet não recebeu "permissão de escrever na tabela". Ele recebeu cinco verbos. O que não tem verbo, ele não faz — não porque a tela esconde, mas porque a função não existe.

4. Quem pode o quê

QuemOpera a TVGera e exclui vídeoAutoriza tablet
admin (PPCP)simsimsim
analistasimsimsim
tablet autorizadosimnãonão
coletor do RitmoProdnãonãonão
visitante (sem login)nãonãonão

Duas naturezas de acesso, de propósito separadas:

  • Pessoa — entra com e-mail e senha, o Supabase devolve um JWT (um crachá que vence em 1 hora e se renova sozinho), e o papel vem da tabela usuarios.
  • Aparelho — não tem e-mail nem senha. Guarda um token de 64 caracteres, entregue uma única vez no pareamento. O banco guarda só o sha256 dele, então nem o banco sabe o token.

5. O caminho de uma ação

Acompanhe o clique em Colocar na TV, do dedo até a tela da fábrica. Quem entende este caminho entende o sistema inteiro.

  1. Na biblioteca, o botão chama colocarNaTV(slug).
  2. A função confere se há acesso; se não, abre o login e guarda a ação pendente para refazê-la depois de entrar.
  3. Chama supaAtivarPainel(slug), no publicar.js. Ali há uma bifurcação: pessoa manda um PATCH em embalagem_config com o crachá; tablet chama a função embalagem_op_ativar com o token.
  4. O banco aplica a RLS (ou a checagem do token) e grava painel_ativo. De quebra, limpa tv_pausa — senão o vídeo novo entraria congelado.
  5. Na fábrica, o player da TV pergunta ao banco de 5 em 5 segundos se há comando (pausa, recarga) e de 1 em 1 minuto se o vídeo mudou.
  6. Percebendo a troca, ele não recarrega a página: troca o conteúdo no lugar. Isso preserva a tela cheia, que o navegador só devolve com alguém apertando um botão lá.

Esse último passo é a decisão mais consequente do projeto — e a origem da armadilha nº 3.

6. Como fazer uma alteração

Rodando na sua máquina

Não precisa instalar nada além de um servidor estático. Abrir o arquivo com duplo clique não funciona (o navegador bloqueia partes do JavaScript em file://).

npx http-server -p 8099 -c-1
# abre http://127.0.0.1:8099/biblioteca.html

Ele vai falar com o banco de produção. Para olhar sem risco, tudo bem. Para testar publicação, use um produto de teste e apague depois.

Publicando

git push na main é o deploy. A Vercel publica em segundos, sem botão nenhum. Não existe homologação: o que entra na main está no ar.

O passo a passo que evita susto

  1. Mude um arquivo só, e pouca coisa de cada vez.
  2. Teste no servidor local, com o navegador aberto no console (F12) para ver erro em vermelho.
  3. Se mexeu em algo do banco, confira antes no SQL Editor do Supabase, com select, o que a sua alteração vai afetar.
  4. Publique e recarregue com Ctrl + F5 — sem isso você pode estar vendo a versão velha e achando que não funcionou.
  5. Se mexeu no player, mande a TV atualizar pela biblioteca. Ela não pega sozinha.
Nunca faça: alterar auth.users por SQL, colocar a chave service_role em qualquer arquivo do site, ou apagar linha de embalagem_paineis pelo painel sem antes tirar o vídeo da TV. E não mexa na Site URL do Supabase: ela é global e o RitmoProd depende dela.

7. Cinco armadilhas (todas já nos pegaram)

1. O e-mail que não existe

Criar conta com domínio que não resolve em DNS dá "Email address is invalid". Foi o que aconteceu com @dispositivo.ritmopatrimar.app. O Supabase confere o domínio.

2. O limite de e-mails

Sem servidor SMTP próprio, o Supabase entrega poucos e-mails por hora. Redefinição de senha e confirmação de conta disputam a mesma cota. Foi daí o "email rate limit exceeded".

3. A TV com o player velho

Como a troca de vídeo não recarrega a página, código novo do player só entra com um reload. Foi por isso que a pausa remota não funcionou na primeira tentativa: o código estava no ar, mas a TV ainda rodava o de antes. O botão Atualizar a TV existe por causa disso.

4. O cache do service worker

O sw.js guarda os arquivos para o gerador abrir sem internet. Ao publicar mudança, aumente o número da versão do cache (ritmopatrimar-embalagem-v15) — senão alguém pode continuar com a versão antiga por dias.

5. Botão escondido não é segurança

Já dito, e vale repetir porque é o erro mais comum de quem começa: esconder o botão não protege nada. A proteção é a policy no banco. Esconder é para a pessoa não clicar em algo que vai ser recusado.

8. Glossário

TermoO que quer dizer aqui
painel / vídeoA mesma coisa. Na tela chamamos de vídeo; no código e no banco ficou painel, da primeira versão.
slugO apelido do produto na URL, sem acento nem espaço: embalagem-nicho-impacto-2-0.
RLS / policyA regra que o banco aplica em toda consulta, dizendo quem pode ler e escrever cada linha.
JWTO crachá de quem fez login. Vence em 1 hora e se renova sozinho pelo refresh token.
token do aparelhoOs 64 caracteres que o tablet guarda no lugar de senha.
RPCChamar uma função do banco pela API, em vez de mexer na tabela direto.
upsertGravar que vira atualização se a linha já existe. É como republicar um vídeo substitui o anterior.
service workerPrograminha que o navegador guarda para servir o site sem internet.
anon / authenticatedOs dois papéis do Postgres que a API usa: visitante e logado.

Por onde começar a mexer

Em ordem de risco, do mais seguro para o mais arriscado:

  1. Textos e cores de qualquer tela. Errou, corrige e publica de novo.
  2. A página inicial (inicio.html): não fala com o banco, é só conteúdo.
  3. A biblioteca: mexer no cartão do vídeo, na ordem, no que aparece.
  4. O player da TV: lembre que roda em navegador antigo — nada de recurso moderno de CSS ou JavaScript, e sempre mande a TV atualizar depois.
  5. O gerador: a leitura do PDF é a parte mais delicada do projeto.
  6. Policies e funções do banco: aqui um erro libera ou bloqueia gente de verdade. Escreva o SQL, leia duas vezes, e teste consultando antes de aplicar.
